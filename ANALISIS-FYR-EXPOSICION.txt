ANÁLISIS TÉCNICO Y FUNCIONAL DE F&R
Material de consulta para exposición oral
Fecha del análisis: 16/10/2026

======================================================================
A. DIAGNÓSTICO GENERAL DE F&R
======================================================================

F&R es una aplicación web para gestionar una tienda de ropa online y
sus operaciones internas. Según el código revisado, permite:

- Mostrar un catálogo de prendas.
- Buscar y filtrar productos.
- Seleccionar talle, color y cantidad.
- Agregar productos al carrito.
- Persistir el carrito por usuario.
- Realizar checkout con envío y método de pago.
- Crear pedidos y sus detalles.
- Consultar compras realizadas.
- Gestionar productos, categorías, proveedores y sucursales.
- Administrar clientes y empleados.
- Registrar ventas presenciales mediante un flujo de empleado/cajero.
- Consultar pedidos, facturas y estados.
- Generar reportes de ventas.
- Consultar compras agrupadas por método de pago.
- Emitir notificaciones.
- Exponer métricas y health checks.

La solución está implementada como dos aplicaciones separadas:

1. FRFront: aplicación web MVC con vistas Razor.
2. FYR-API: API REST basada principalmente en Minimal APIs.

El frontend se comunica con la API mediante HttpClient usando como base:

    http://localhost:5097/

La base de datos configurada es:

    SQL Server local
    Base: FYR_DB

Arquitectura principal:

    Usuario
      |
      v
    FRFront - MVC / Razor Views
      | HttpClient
      v
    FYR-API - Minimal APIs
      |
      v
    Servicios / Repositorios
      |
      v
    Entity Framework Core
      |
      v
    SQL Server - FYR_DB

Estado general:

- Catálogo: implementado.
- Carrito: implementado, con validaciones parciales.
- Checkout: implementado como simulación de pago.
- Pedidos: implementado.
- Detalles de pedido: implementado.
- Gestión de productos: implementada.
- Gestión de clientes: implementada.
- Gestión de empleados: implementada.
- Reportes: implementados.
- Métricas: implementadas parcialmente.
- Autenticación: implementada parcialmente.
- Autorización real de API: no demostrada.
- Multiempresa: modelo preparado, aislamiento no demostrado.
- Tests automatizados: no detectados.

RF-03. REALIZAR UNA COMPRA ONLINE

Descripción:

El cliente puede seleccionar envío, método de pago, cuotas y confirmar
un pedido.

Necesidad:

Permite completar el proceso comercial:

    Carrito -> Envío -> Pago -> Pedido

Actor:

Cliente.

Archivos:

- Codigo/FRFront/Controllers/CheckoutController.cs
- Codigo/FRFront/Views/Checkout/Envio.cshtml
- Codigo/FRFront/Views/Checkout/Pago.cshtml
- Codigo/FRFront/Views/Checkout/CompraExitosas.cshtml
- Codigo/FYR-API/Endpoints/PedidoEndpoints.cs
- Codigo/FYR-API/Endpoints/DetallePedidoEndpoints.cs
- Codigo/FYR-API/Entidades/Models/Pedido.cs
- Codigo/FYR-API/Entidades/Models/DetallePedido.cs

Endpoints:

- POST /api/pedidos
- POST /api/pedidos/{id}/detalles
- PUT /api/usuarios/{id}/carrito

Medios:

- Efectivo.
- Tarjeta de débito.
- Tarjeta de crédito.
- Transferencia.

Reglas:

- Efectivo: disponible para retiro local y aplica descuento.
- Crédito en 6 cuotas: aplica recargo.
- Crédito en 12 cuotas: aplica recargo mayor.
- Se persiste el método de pago.
- Se guarda la cantidad de cuotas.
- Se muestra el monto de cada cuota en Mis compras.

Demostración:

1. Iniciar sesión como cliente.
2. Agregar productos.
3. Elegir envío.
4. Elegir método de pago.
5. Elegir cuotas si corresponde.
6. Confirmar.
7. Mostrar compra exitosa.
8. Entrar a Mis compras.
9. Mostrar método, total, cuotas e ítems.

Validaciones:

- Usuario obligatorio.
- Carrito no vacío.
- Método obligatorio.
- Datos de tarjeta obligatorios para débito y crédito.
- Error si la API no responde.
- Error si no se encuentra el usuario.

Estado:

Implementado como flujo comercial simulado.

No se encontró una integración con una pasarela real de pagos. Se
verifica la existencia de datos de tarjeta, pero no una autorización
bancaria real.

======================================================================
G. FUNCIONALIDADES Y ASPECTOS TÉCNICOS IMPORTANTES
======================================================================

DTOs:

Separan las entidades internas de los datos enviados o recibidos por la
API. Ejemplos: PedidoResponse, CreatePedidoRequest, ProductoResponse y
DetallePedidoResponse.

REPOSITORIOS:

Encapsulan consultas de Entity Framework. El recorrido esperado es:

    PedidoEndpoint
      -> PedidoService
      -> IPedidoRepository
      -> PedidoRepository
      -> AppDbContext

SERVICIOS:

Aplican reglas de negocio y mapean entidades a respuestas. Por ejemplo,
PedidoService crea pedidos, actualiza estados y actualiza seguimiento.

ENDPOINTS:

Reciben solicitudes HTTP y devuelven respuestas. El frontend no accede
directamente a SQL Server: consume la API mediante HttpClient.

MIGRACIONES:

El proyecto tiene migraciones versionadas para:

- Modelo inicial.
- Cambio de fechas.
- DNI de usuario.
- Imagen de notificaciones.
- Persistencia del carrito.
- Sucursal del usuario.
- Datos de proveedor.
- Datos de contacto.

MULTIEMPRESA:

El modelo contiene EmpresaId en usuarios y productos, y existen
empresas, sucursales y proveedores.

Sin embargo, no se observó un mecanismo completo de tenant context ni
filtros globales por empresa.

Forma correcta de explicarlo:

"El sistema tiene preparado el modelo para relacionar datos con
empresas, pero el aislamiento entre comercios todavía no está
demostrado en todas las consultas y operaciones."

======================================================================
I. LIMITACIONES, PARTES INCOMPLETAS Y MEJORAS FUTURAS
======================================================================

I.1. AUTORIZACIÓN BACKEND

Problema:

Se generan JWT, pero no se observó su validación efectiva en la API.

Mejora:

Configurar AddAuthentication, AddJwtBearer, AddAuthorization,
UseAuthentication, UseAuthorization, RequireAuthorization y políticas
por rol.

I.2. MULTIEMPRESA

Problema:

Existe EmpresaId, pero no se observan filtros obligatorios por empresa.

Mejora:

- Tenant context.
- Empresa obtenida desde el token.
- Filtros globales.
- Validación de pertenencia.
- Tests de aislamiento.

I.3. PAGO REAL

Problema:

El checkout recibe datos de tarjeta y calcula recargos, pero no conecta
con una pasarela.

Mejora:

Integrar un proveedor real y nunca almacenar datos completos de tarjeta.

I.4. RECUPERACIÓN DE CONTRASEÑA

Problema:

Los tokens se almacenan en un diccionario estático y se devuelven
directamente.

Mejora:

- Token seguro.
- Hash del token en base.
- Expiración.
- Uso único.
- Envío por email.
- Invalidación después del cambio.

I.5. TRANSACCIONES DE VENTA

Problema:

Pedido, detalle, factura, pago y stock no aparecen coordinados en una
única transacción.

Mejora:

Usar una transacción que incluya pedido, detalles, pago, factura y
actualización de stock. Incorporar idempotencia.

I.6. RENDIMIENTO

Problema:

Varias consultas traen listas completas de usuarios, pedidos,
productos o facturas.

Mejora:

- Paginación.
- Filtros server-side.
- Consultas por ID.
- Proyección directa a DTO.
- Índices.

I.7. CONFIGURACIÓN Y SECRETOS

Problema:

Hay URLs, claves y configuraciones sensibles hardcodeadas.

Mejora:

Usar appsettings por ambiente, variables de entorno, Secret Manager y
un sistema de secretos.

I.8. PRUEBAS

No se detectó un proyecto de pruebas automatizadas mantenido.

Se recomienda agregar:

- Tests unitarios.
- Tests de integración.
- Tests de autorización.
- Tests de carrito.
- Tests de cuotas.
- Tests multiempresa.
- Tests de concurrencia.

J. PREGUNTAS TÉCNICAS DEL PROFESOR
======================================================================

¿POR QUÉ SEPARARON FRONTEND Y BACKEND?

Respuesta:

El frontend se ocupa de la interacción y presentación, mientras que la
API concentra acceso a datos y operaciones de negocio. Esto permite que
la API pueda ser consumida por otros clientes en el futuro.

Archivos:

- Codigo/FRFront/Program.cs
- Codigo/FYR-API/Program.cs

----------------------------------------------------------------------

¿DÓNDE SE GUARDA UN PEDIDO?

Respuesta:

El frontend envía el pedido a POST /api/pedidos. La API lo transforma
en una entidad Pedido y lo persiste mediante Entity Framework y SQL
Server. Luego se registran sus detalles mediante el endpoint de
detalles.

Archivos:

- Codigo/FYR-API/Endpoints/PedidoEndpoints.cs
- Codigo/FYR-API/Logica/Services/PedidoService.cs
- Codigo/FYR-API/Repositorios/Implementaciones/PedidoRepository.cs

----------------------------------------------------------------------

¿CÓMO SE RELACIONA UN PEDIDO CON SUS PRODUCTOS?

Respuesta:

Mediante DetallePedido. Cada detalle posee PedidoId, ProductoId,
cantidad, precio unitario y subtotal.

Archivos:

- Codigo/FYR-API/Entidades/Models/DetallePedido.cs
- Codigo/FYR-API/Logica/DTOs/DetallePedido/Responses/
  DetallePedidoResponse.cs

----------------------------------------------------------------------

¿CÓMO FUNCIONAN LOS ROLES?

Respuesta:

Los roles existen como enum y se incluyen en el token generado. En el
frontend se guarda el rol en sesión para decidir la navegación. La
autorización efectiva de la API debe reforzarse porque no se encontraron
políticas Authorize aplicadas de forma uniforme.

Archivos:

- Codigo/FYR-API/Entidades/Enums/Rol.cs
- Codigo/FYR-API/Logica/Services/AuthService.cs
- Codigo/FRFront/Controllers/AccountController.cs

----------------------------------------------------------------------

¿EL PAGO ES REAL?

Respuesta:

Actualmente es un flujo de checkout simulado. Se validan datos básicos
y se calculan descuentos, recargos y cuotas, pero no se observa una
integración con un procesador bancario.

Archivos:

- Codigo/FRFront/Controllers/CheckoutController.cs
- Codigo/FRFront/Views/Checkout/Pago.cshtml

----------------------------------------------------------------------

¿EL SISTEMA PERMITE MÚLTIPLES COMERCIOS AISLADOS?

Respuesta:

El modelo incluye empresas y relaciones con productos, usuarios y
sucursales. Sin embargo, no se observa un mecanismo completo de
aislamiento por empresa en las consultas, por lo que no se debe
presentar como multiempresa seguro todavía.

Archivos:

- Codigo/FYR-API/Entidades/Models/Empresa.cs
- Codigo/FYR-API/Entidades/Models/Usuario.cs
- Codigo/FYR-API/Datos/AppDbContext.cs

----------------------------------------------------------------------

¿QUÉ PASA SI SE CAE LA BASE DE DATOS?

Respuesta:

La API tiene /api/health para verificar la conexión. Durante el
arranque registra el error si la base no está disponible. En el
frontend, algunas pantallas muestran mensajes o utilizan datos de
respaldo en memoria.

Archivos:

- Codigo/FYR-API/Program.cs
- Codigo/FRFront/Controllers/HomeController.cs

----------------------------------------------------------------------

¿QUÉ TECNOLOGÍAS DE MONITOREO UTILIZAN?

Respuesta:

La API expone métricas Prometheus mediante /metrics, tiene una métrica
propia de intentos de pedidos y se documenta una integración con
Prometheus y Grafana.

Archivos:

- Codigo/FYR-API/Metricas/MetricasTienda.cs
- Codigo/FYR-API/Program.cs
- monitoring/README.md
